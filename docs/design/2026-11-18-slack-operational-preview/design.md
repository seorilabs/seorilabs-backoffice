# 광고 보상과 결제 푸시의 첫 줄 보정

사용자가 2026-11-18에 광고 보상 푸시에는 보상 이름만 보여 알기 어렵다고 제보하고, 결제에도 같은 형식이면 보정하도록 지시했다. 구현·검증·PR 병합은 [#594](https://github.com/seorilabs/seorilabs-backoffice/pull/594)로 완료했다. 이어 같은 대화에서 사용자가 “배포도 해”라고 지시하여 출시 범위를 서비스 운영 배포와 정상 상태 확인까지 넓혔다. 이 지시를 승인 근거로 테스트 계획의 `release`를 `service`·`public`으로 기록한다. 실행 티켓: [#593](https://github.com/seorilabs/seorilabs-backoffice/issues/593). 기존 [#580](https://github.com/seorilabs/seorilabs-backoffice/issues/580)의 사용자 화면 검수 이력은 유지한다.

## 문제와 동작

현재 앱·플랫폼·처리 결과는 Slack `header`에 있고 첫 `rich_text`는 보상명 또는 지급항목으로 시작한다. 최상위 `text`에는 기존 제목도 있으므로 실제 휴대폰에서 어떤 필드를 표시했는지는 이번 코드 검사만으로 확정할 수 없다. [Slack 공식 문서](https://docs.slack.dev/reference/methods/chat.postMessage/#the-text-blocks-and-attachments-fields)는 최상위 `text`를 알림과 화면 읽기에 사용한다고 설명한다. 두 경로 모두 첫 줄만으로 이해할 수 있게 만든다.

합성 자료의 변경 후 예시:

```text
🎬 [예제 앱 · Android] 광고 보상 지급 완료 — crystal: 10
💳 [예제 앱 · 구글플레이] 실제 주문 결제 발생 — 지급항목: premium
💳 [예제 앱 · 앱스토어] 테스트 주문 구매 복원 — 지급항목: premium
❌ [예제 앱 · Android] 광고 보상 지급 실패 — 오류: PROVIDER_TIMEOUT
```

## 구조와 데이터

`operationalInterestCard`가 광고·결제 알림에 기존 표시 계약의 선택 레이아웃 `compact`를 지정한다. 앱을 앞에 두고 첫 지급항목 또는 오류를 제목에 합친다. Slack 렌더러는 이 레이아웃의 제목을 첫 `rich_text` 블록에 문자 그대로 넣고 같은 문장을 최상위 `text`의 첫 줄로 만든다. 별도 header나 중복 요약은 만들지 않는다. 다른 알림 레이아웃은 유지한다.

기존 국가, 결제 사용자 ID, 실패 진단, 발생 시각은 후속 블록에 보존한다. 0과 미제공, 실제·테스트·미확인 주문, 신규 결제·복원·소유권 이전·권리 지급·마켓 완료 처리 실패를 구분한다. 보상·상품의 내부 식별자를 임의의 상품명으로 번역하지 않는다. 새로운 개인정보나 운영 API는 추가하지 않는다. 원장·발송 경로·중복 방지·재시도·과거 메시지는 변경하지 않는다.

공통 제목을 전부 바꾸면 다른 보고서에도 영향을 주므로 광고·결제에만 이 레이아웃을 사용한다. 제목과 본문 양쪽에 문장을 복제하는 방식은 중복 표시를 만들기 때문에 사용하지 않는다.

## 인수조건과 검증

- AC-1: 광고 성공·실패의 첫 본문 블록과 최상위 `text` 첫 줄에 앱·플랫폼·결과·보상 또는 오류가 있다.
- AC-2: 결제에서도 앱·마켓·주문 구분·처리 종류·지급항목 또는 오류가 같은 첫 줄에 있다.
- AC-3: 0·누락값·국가·사용자 ID·실패 진단·발생 시각 및 식별자의 특수문자를 보존하며 요약을 반복하지 않는다.
- AC-4: 저장 payload 왕복 후 같은 메시지를 만들고 모의 `chat.postMessage` 요청에도 같은 `text`와 `blocks`를 보낸다.

L1 서비스 개발 환경에서 합성 이벤트로 검증한다. 먼저 새 요구사항으로 테스트 4개가 실패하는 것을 확인한 뒤 구현했다. 관련 회귀, 전체 테스트, typecheck, lint, 웹·worker 빌드를 실행한다. 새 화면·제품 UI 개편이나 네이티브 SDK 변경은 아니다. 실제 Slack 발송·휴대폰 푸시 표시는 실행하지 않으며 이번 테스트 통과를 실제 화면 검수로 표시하지 않는다.

## 적용과 복구

배포 승인 기록을 병합한 최종 후보 SHA에서 서비스 실행 근거를 확인하고 중앙 검증기를 통과한 뒤 기존 `deploy.yml`의 명시적 `workflow_dispatch`와 `deploy=true`로 운영에 배포한다. 웹·알림 worker 등 기존 workload의 source SHA, immutable image digest와 준비 상태, 공개 health를 다시 읽어 확인한다. 운영 적용 시에는 새로 생성되는 알림부터 바뀌며 이미 저장된 payload와 과거 메시지는 유지한다. 되돌릴 때는 직전 정상 이미지와 배포 런북을 사용한다. 실제 결제·광고 이벤트를 만들거나 테스트 메시지를 운영 Slack에 보내지 않는다. 사용자 휴대폰의 푸시 표시는 별도 실제 화면 확인이며 이번 배포 완료의 증거로 주장하지 않는다.
