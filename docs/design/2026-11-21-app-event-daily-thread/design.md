# 앱이벤트·광고보상 일자별 쓰레드 묶기

`#앱이벤트`(action-events)와 `#광고보상`(ad-rewards) 채널의 앱 이벤트를 건마다 새 메시지로 보내던 방식을, KST 기준 날짜와 앱이 같은 이벤트들을 하나의 쓰레드로 모으는 방식으로 바꾼다. 같은 폴더의 `test-plan.json`을 함께 승인받는다.

## 문제와 동작

플랫폼 운영 이벤트는 그날 들어온 앱별로 한 줄씩 스택에 쌓인다. 같은 앱의 하루를 한눈에 보고 그 흐름을 따라가려면 스크롤을 계속해야 한다. 읽는 사람이 필요한 것은 "오늘 이 앱에 무슨 일이 있었나"이고, 그 답은 한 줄짜리 원문보다 **날짜·앱·건수·마지막 갱신 시각이 적힌 본메시지 하나와 그 아래 댓글 목록**에 있다.

합성 자료의 변경 후 예시(`#앱이벤트`):

```text
**[블룸핸드]** 2026-11-21 앱이벤트 12건 · 마지막 업데이트 14:32
  └ 댓글: **[블룸핸드:1.0.3]** 신규계정#1 - firebase / ios / 09:12
  └ 댓글: **[블룸핸드:1.0.4]** 신규계정#2 - firebase / ios / 14:32
```

- 그날·그 앱의 첫 이벤트가 오면 채널 루트에 본메시지 하나를 만든다.
- **첫 이벤트 본문도 본메시지에 중복 게시하지 않고 쓰레드 첫 댓글로 싣는다.** 본메시지는 요약 전용이다.
- 같은 날 같은 앱의 다음 이벤트는 같은 쓰레드의 댓글로 싣는다.
- 본메시지는 날짜, 앱 이름, 그날 그 채널로 들어온 이벤트 건수, 마지막 이벤트 시각을 담고, 댓글이 늘 때마다 같은 메시지를 편집해 갱신한다.
- `#광고보상`도 같은 규칙을 쓴다. `#결제알림`(iap)은 이번 범위가 아니라 건별 메시지를 유지한다.

## 구조와 데이터

`src/lib/platform/app-event-thread.ts`가 쓰레드 계약의 한 곳이다.

- **단위**: (목적지, KST 날짜, 플랫폼 앱 id). 날짜 축은 `metric-day.ts`의 KST 정본을 쓴다. 앱 식별자는 플랫폼이 보낸 `appId`를 쓰고 표시 이름만 따로 가져온다.
- **목적지 해석**: `operationalDestinationKey(type)`이 이벤트 종류를 결제·광고·기타로 나누고 전용 채널 설정 여부에 따라 최종 목적지를 정한다. 전용 채널이 없으면 기존 폴백 규칙(`ad-rewards` → `action-events`, `iap` → `action-events`)을 그대로 따른다. 해석은 한 곳에서만 하고 라우트와 건수 계산이 같은 값을 쓴다.
- **부모(본메시지)**: `notification_event` 한 건이다. dedupeKey 는 `operational-thread:{destinationKey}:{day}:{appId}`. 그 `notification_delivery.providerMessageId`가 곧 Slack 쓰레드 루트 ts다. **새 스키마를 만들지 않는다.**
- **댓글**: 기존 dedupeKey `operational:{eventId}`를 그대로 쓴다. 댓글 payload 에 `appEventThread` 로 부모 dedupeKey 를 넣고, 부모 payload 에는 그 키가 없다. 이 차이로 본메시지와 댓글을 구분한다(`thread` 키는 이슈 알림 쓰레드 계약의 자리라 쓰지 않는다).
- **건수**: `operational_event` 원장에서 그날·그 앱·같은 목적지로 해석되는 이벤트 수를 센다. 사용자가 2026-11-21에 "그날 들어온 이벤트 수"로 확정했다. 댓글 게시 성공 수로 세는 안은 `occurredAt` 이 다른 재전송에서 중복 댓글 위험을 만들므로 기각했다.
- **갱신**: 라우트가 부모 payload 를 다시 쓰면서 `enqueueEditableNotification` 을 쓴다. 본문 `text` 가 `reportFingerprint` 에 들어가므로 건수가 바뀌면 자동으로 재게시 예약이 되고, 워커가 `chat.update` 로 같은 메시지를 편집한다. 첫 이벤트면 부모가 새로 생겨 루트 메시지가 된다.
- **댓글 게시**: 워커(`src/lib/notifications/deploy.ts`)가 부모의 `providerMessageId` 를 찾아 `replyToMessageId` 로 넘긴다. `channel.ts` 가 `chat.postMessage` 의 `thread_ts` 에 넣는다. 부모가 아직 안 나갔으면 "부모 앱이벤트 알림 발송 대기 중" 실패로 돌려 재시도에 맡긴다. 이슈 알림 쓰레드와 같은 방식이다.

`NotificationKind` 에 값 을 추가하지 않는다(MySQL ENUM 변경은 expand-only 게이트가 막는다). 쓰레드 구분과 편집 대상은 payload 로 한다.

## 인수조건과 검증

- AC-1: 첫 이벤트는 루트 메시지 하나와 쓰레드 첫 댓글 하나를 만들고, 루트 본문에 이벤트 본문이 없다.
- AC-2: 같은 날 같은 앱의 다음 이벤트는 새 루트가 없고 같은 `thread_ts` 에 댓글로 붙는다. 다른 앱·다른 날은 다른 루트를 만든다.
- AC-3: 본메시지에 날짜·앱 이름·건수·마지막 갱신 시각이 있고, 댓글이 늘면 `chat.update` 로 갱신된다.
- AC-4: `#광고보상` 도 같은 규칙으로 묶인다. `#결제알림` 은 건별 메시지 그대로다.
- AC-5: 같은 이벤트를 재전송해도 원장·부모·댓글이 늘지 않는다.
- AC-6: 부모가 아직 게시되지 않았으면 댓글은 대기 상태로 남고, 부모가 게시되면 붙는다.
- AC-7: 배포 카드, incident, 이슈 쓰레드, 일일 지표, 재무 리포트의 게시·편집이 바뀌지 않는다.

L1, 개발 환경. 단위 테스트와 라우트 계약 테스트는 DB 이중 계측으로 확인하고, 종단 검증은 실제 MySQL 과 합성 Slack API 로 `scripts/test-app-event-thread.ts` 가 확인한다(실제 Slack 채널에는 아무것도 보내지 않는다). 전체 테스트, typecheck, lint, build 를 실행한다. 기기 실행은 필요 없다.

## 적용과 복구

스키마 변경이 없어 migration 이 없다. 알림 워커와 웹 이미지를 배포한 뒤 새로 발생하는 이벤트부터 새 모양이 적용된다. 이미 게시된 메시지는 그대로 남고, 저장된 payload 는 이전 코드로 돌아가도 무시된다. 되돌릴 때는 직전 이미지를 쓴다. 운영 배포는 승인된 테스트 계획의 `service` 범위 안에서 진행하며, 실제 확인은 자연 발생 이벤트를 관찰하는 것으로 한다(합성 이벤트를 운영 채널에 보내지 않는다).
