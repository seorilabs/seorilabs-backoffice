## 목적·범위·현재 근거

카드 하나만 읽어도 대상 앱, 변화, 조회 영향, 다음 행동을 알 수 있게 한다. 수집 실패를 앱 장애나 심사 거절로 오해하지 않도록 수집 대상 업무를 제목에 쓴다.

2026-10-11 15:59 KST에 운영 DB를 읽기 전용 조회한 결과, 사용자가 제시한 두 수집 알림은 모두 `com.seorilabs.mergearmada`, **머지 함대: 합치고 싸워라**에 대한 것이다.

| 한국 시간 | 실제 수집 기록 | 의미 |
| --- | --- | --- |
| 15:00:53 | `observed`, 릴리스 3건 | 정상 수집 |
| 15:15:52 | `needs_input`, `SOURCE_PERMISSION_REQUIRED`, 확인한 릴리스 0건 | 권한·설정 관련 오류로 분류된 조회 실패 |

| 15:45:52 | `observed`, 릴리스 3건 | 정상 수집 회복 |

`SOURCE_PERMISSION_REQUIRED`는 현재 코드가 401·403 또는 권한·설정 관련 오류 문구를 묶어 붙인 분류다. 이 기록만으로 영구적인 권한 상실이나 실제 설정 변경 필요성을 확정하지 않는다. 15:45의 정상 응답도 앱의 신규 승인·공개를 뜻하지 않는다.

검색 순위는 Apple 검색 API 결과 최대 200개 중 해당 앱의 위치다. 숫자가 작아지면 앞쪽으로 이동한 것이다. 실제 기기 화면의 순위·검색 유입량·매출 변화는 이 자료로 확정하지 않는다.

| 실제 관측 | 쉬운 표현 |
| --- | --- |
| `KR 해전 50 → 36` | 한국 App Store · “해전” · 50위 → 36위, 14계단 상승 |
| `KR naval battle 93 → 100` | 한국 App Store · “naval battle” · 93위 → 100위, 7계단 하락 |

제시된 네 카드의 해설 상태는 모두 `FALLBACK / ANALYSIS_FORMAT_INVALID`였다. “현재 자료만으로 원인 확정할 수 없음 / 원본 출처와 수집 범위 확인 필요”는 실제 원인 분석이 아니라 해설 실패 시 반복하는 고정 문구다.

## 사용자 흐름·카드 상태

공통 읽는 순서는 **변화 제목 → 앱 → 핵심 사실 → 영향 또는 확인할 일 → 출처·한국 시간 → 상세 링크**다. 상태 이름이나 색만으로 의미를 전달하지 않는다.

### `#ops-alerts` — 조회 실패

> **Google Play 출시 상태 조회 실패**<br>
> 머지 함대: 합치고 싸워라<br>
> 오류: 권한·설정 관련 오류로 분류됨<br>
> 영향: 이번 조회에서 출시 현황을 갱신하지 못함<br>
> 확인할 일: 다음 수집 결과 확인. 계속 실패하면 Play 접근 권한 점검<br>
> [수집 이력 보기]<br>
> 10월 11일 15:15 KST · Google Play 출시 상태 수집

코드 내부 `source-stale`는 실패·지연·설정 부족을 함께 다루므로 실제 상태에 따라 **조회 실패 / 수집 지연 / 수집 설정 확인 필요**를 구분한다. 권한 오류 분류를 “권한이 없어짐”으로 단정하지 않는다. 마지막 정상 시각·오류 코드를 확보한 경우 표시하고, 없으면 “기록 없음”으로 표시하거나 해당 줄을 생략한다.

### `#ops-alerts` — 회복

> **Google Play 출시 상태 조회 회복**<br>
> 머지 함대: 합치고 싸워라<br>
> 결과: 릴리스 3건 확인 · 정상 수집 재개<br>
> [수집 이력 보기]<br>
> 10월 11일 15:45 KST · Google Play 출시 상태 수집

회복 건수는 `SourceCollectionRun.coverage`의 실제 수집 건수만 사용한다. 빈 정상 응답은 **응답 회복 · 조회 결과 없음**으로 구분하고 “릴리스 0건으로 줄어듦”이라고 쓰지 않는다. 건수가 없으면 정상 응답 사실만 쓴다.

### `#metrics-daily` — 상승·하락

> **App Store 검색 순위 상승**<br>
> 머지 함대: 합치고 싸워라<br>
> 한국 App Store · 검색어 “해전”<br>
> **50위 → 36위 · 14계단 상승**<br>
> Apple 검색 API의 이전 수집 결과와 비교 · 최대 200개 결과 기준<br>
> 실제 기기 검색 순위와 다를 수 있음<br>
> [검색 순위 근거 보기]<br>
> 10월 11일 12:20 KST

하락은 “93위 → 100위 · 7계단 하락”으로 같은 구조를 사용한다. 첫 200개 결과에 새로 나타나면 **검색 결과 진입**, 사라지면 **검색 결과에서 벗어남**으로 표시한다. `null`을 정확한 201위나 0위로 바꾸지 않는다. 비교 시점이 전날이라고 확인되지 않으면 “전일 대비” 대신 “이전 수집 대비”라고 쓴다.

### AI 해설과 알려지지 않은 상태

- 수집·검색 순위 카드의 의미와 확인할 일은 검증된 사실·상태 규칙으로 완성한다. AI 해설 실패가 카드 이해를 막지 않는다.
- 유효한 해설만 짧게 덧붙이고 추론은 “가능한 원인”처럼 구분한다. 실패·대기 시 고정 가설과 “해설 없음 / 준비 중” 줄은 이 카드에서 생략한다. 실제 분석 상태·실패 사유는 기존 상세 화면에 유지한다.
- 내부 source 이름·event kind는 상세 근거에서 보존한다. 카드에는 `play-submissions` 대신 “Google Play 출시 상태”, `source-recovery` 대신 “수집 회복”처럼 표시한다.
- 미등록 소스·앱명 없음은 “외부 자료 수집 / 대상 앱 확인 필요”처럼 미확인 사실을 드러낸다. 다른 앱명을 추측하지 않는다.
- 상세 링크가 있는 메시지이며 신규 확인 버튼이나 승인 동작은 추가하지 않는다. 취소·키보드 입력 상태는 해당 없음이다.
- 작은 화면·큰 글자는 같은 순서로 줄바꿈한다. 국가·단위·순위 방향·변화량을 글자로 표시한다.

## 구조·책임·데이터

기존 **수집 원장 → 신호 생성 → 공통 카드 본문 → 알림 outbox → Discord 전송** 경계를 재사용한다.

| 대상 | 변경 책임 |
| --- | --- |
| `src/lib/insights/triggers.ts` | 수집 신호에 앱 표시명·실제 상태·오류 분류·정상 시각·회복 수집 건수를 안전한 근거로 포함 |
| `src/lib/insights/contract.ts` | 기존 카드 렌더러에 쉬운 표시명·카드 유형별 문구와 의미 있는 상태별 확인 행동 적용 |
| `src/lib/insights/service.ts` | 사실 카드와 분석 후 편집 카드가 같은 구조 사용. 카드 제목·링크·KST 시각 표시 |
| `src/lib/market/collector.ts` | #452의 순위 계산을 재사용하고 국가·검색어·기준 문구 정리 |
| 관련 테스트·운영 적용 문서 | 문구·실패 경로·실행 버전 확인을 검증 |

새 테이블·migration·자격증명·API·작업 대기열은 만들지 않는다. 새 신호의 근거만 기존 evidence 규약의 길이 제한 안에서 작성한다. 과거 신호 payload는 수정하지 않는다. 원본 수집 실패 분류·AI 문서 상태·멱등성·재시도·전송 대상과 기존 비밀값 차단을 유지한다. 긴 앱명·검색어는 기존 안전한 길이 제한과 멘션 제거를 사용한다.

| AC-8 | 운영 적용 후 두 실행기와 실제 Pod가 승인 후보 digest 사용 | 승인 후 provider readback, 다음 자연 수집의 payload·메시지 확인 |

- TDD: AC-1~7의 기존 불충분한 표시를 먼저 실패로 재현한 뒤 구현한다. 프로덕션 오류 재발이나 실제 발송은 단위 테스트의 통과 조건으로 만들지 않는다.
- 제품 UI와 Discord 카드의 실제 렌더링을 수정하면 승인 후 작성자와 다른 검수자가 개발 실행 환경에서 기능·UX를 3회 확인한다. 회차별 계획·격리 자료·후보·증거를 남기며 추가 회차는 사전 승인을 받는다.

- 실제 Discord 서버에 시험 메시지를 보내는 승인은 포함하지 않는다. 실제 Discord 화면 검수가 불가능하면 그 항목은 미검수로 기록하고 개발 렌더링 검증과 구분한다.
- 구현 후 `pnpm typecheck`, `pnpm lint`, 관련 테스트와 전체 `pnpm test`, 더미 `DATABASE_URL`의 `pnpm build`를 실행한다.
- 운영 후보의 빌드·배포 전 E2E는 기존 전체 기능 목록과 중앙 계약을 사용한다. 미실행 항목은 통과로 기록하지 않는다. 설계 HTML 렌더링은 제품 E2E가 아니다.

## 적용·복구·승인 추적

1. v1의 정확한 설계 커밋·범위가 승인되면 실행 Issue를 연결하고 제품 코드를 구현·검증한다. Ready PR·CI 통과 후 저장소 정책에 따라 squash merge한다.
2. 운영 적용까지 승인된 경우에만 같은 후보 SHA의 개발 E2E와 immutable image를 고정한다. 기존 trusted operator 경계로 `backoffice-operations-insights`와 `backoffice-market-feedback`의 **이미지만** 갱신하며 활성 replica·suspend·스케줄·설정은 보존한다. 일반 웹·전송 실행기도 후보와 대조한다. 신규 리소스나 권한 확대는 하지 않는다.
3. 다음 자연 수집·분석에서 만들어진 신호·outbox·provider message ID와 실제 메시지를 읽어 새 문구 적용을 확인한다. 시험 전송·수동 수집·과거 메시지 편집은 별도 승인 없이는 하지 않는다.
4. 문제가 있으면 승인된 이전 digest로 이미지 복구한다. 관측·분석 기록은 보존하고 불명확한 전송 결과를 반복 발송하지 않는다.
5. 구현·병합·운영 적용·실제 메시지 확인을 각각 보고한다. 최종 승인 기록에는 승인 커밋·선택 범위·대화 근거와 Issue·PR·검수 링크를 붙인다. 승인 없는 항목을 사후 승인으로 작성하지 않는다.

승인 전에는 문서·시안·읽기 전용 조사만 수행한다. Wiki·Obsidian은 이 원본 설계의 링크와 승인 상태만 기록하며 본문을 복제하지 않는다.
