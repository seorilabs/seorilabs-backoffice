# 정기 검색 순위 보고 실패 복구

하루 세 번 검색 순위 보고를 받는 승인 범위의 결함을 고친다. 원래 계약은 [검색 순위 수집 확대](../2026-10-28-keyword-frequency-and-play/design.md)이며, 2026-10-30 사용자 제보는 “앱 순위에 대한 알림은 좀 더 빈번하게 받고 싶다고 했었는데 안오네?”다. 기존 횟수, 검색어와 국가, 관측 원장, 소개할 항목 선별 및 알림 구성은 바꾸지 않는다.

## 관측과 수정 범위

운영 수집은 하루 3회 활성 상태다. 2026-10-29 14:40, 21:40과 10월 30일 08:40 KST 보고 Job은 실패했고, Slack 보고 이벤트도 만들어지지 않았다. 오늘 수집 411행과 과거 이력 3,857행을 읽은 진단에서 조회 합계는 1초 미만이지만 보고 계산 전체는 약 64초였다. 운영 코드는 30초 트랜잭션 안에서 이력을 반복 선형 탐색한다. 같은 자료를 격리 MySQL 9.2에 복사한 개발 실행은 1초의 압축된 트랜잭션 예산에서 7.1초 뒤 P2028 만료 오류가 났다. 운영 데이터는 읽기만 했고 진단의 모든 쓰기는 차단했다.

이력을 기존 시각 내림차순으로 정렬한 뒤 행 식별자와 KST 날짜별 조회표를 한 번 만든다. 각 현재 행은 그 조회표에서 이전 성공 관측과 일별 점을 읽는다. 동률일 때 먼저 나온 관측 우선, 마켓과 출처 및 언어 분리, 현재 회차 우선, 첫 관측과 결측 표현을 유지한다. 트랜잭션 제한과 Job 자원, 일정은 늘리지 않는다. UI 구조와 DB 스키마, 운영 설정 변경은 없다.

## 인수조건과 검증

- AC-1: 411개 현재 관측과 3,857개 과거 관측 규모에서 보고를 생성하고 트랜잭션 만료가 없어야 한다. 1초 예산의 격리 DB 압축 실행과 원래 30초 예산 실행을 각각 기록한다.
- AC-2: 기존 비교 결과와 28일 점, 정렬 동률, 마켓과 국가 및 언어 분리, 결측, 현재 회차 우선이 같다. 큰 변화와 미소개 항목 최대 3개, 브랜드 최대 1개 선별을 유지한다.
- AC-3: 재실행은 같은 회차 이벤트와 Slack delivery 1개를 유지한다. 아침, 오후, 저녁 회차는 별도 이벤트다. 관측이나 중앙 설정은 수정하지 않는다.
- AC-4: 타입 검사, lint, 전체 테스트와 웹 및 worker 빌드를 통과하고 Ready PR, 로컬 코드 리뷰와 required check를 거친다.
- AC-5: 운영 반영 뒤 검증 후보와 이미지, 일정 유지, 오늘 실패한 현재 회차의 복구 결과와 Slack 수신을 대조한다. 복구 실행을 정시 자연 실행으로 기록하지 않는다. 과거 여러 회차를 일괄 재발송하지 않는다.

L1 개발 환경에서 바뀐 검색 관측과 알림 서비스의 실제 격리 DB 실행을 검증한다. 기존 화면 구성은 유지하므로 UI 개편이나 기기 검수는 해당하지 않는다. 자료와 원본 실패를 NAS에 검증 보관한다.

## 적용과 복구

승인된 정기 보고의 정상 동작 복구로 한정해 구현, PR 병합, service 운영 적용과 현재 실패 회차 1건 복구까지 진행한다. 문제가 남으면 기존 운영 이미지로 되돌리며 수집 이력, 국가와 검색어, 설정 revision을 삭제하거나 덮어쓰지 않는다. 승인 근거는 원래 보고 확대 승인과 이번 결함 제보이며 새로운 발송 정책 승인을 주장하지 않는다.

현재 공개 후보 4e64f79와 squash main의 파일 내용은 같지만 이력이 갈라져 있으므로, 파일 변경 없는 merge로 후보 조상을 연결했다. 검증 기준은 실제 공개 후보이며 원래 저장소의 사용자 작업은 별도 worktree로 보존한다.
