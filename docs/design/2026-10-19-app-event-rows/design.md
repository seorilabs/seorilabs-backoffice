# 앱 운영 이벤트 건별 알림 복원

사용자 선택: 「건별 알림 복원: 신규 계정과 새 버전 첫 유입을 다시 발송」. 앞선 「코드와 운영상태 변경해」와 이번 선택에 따라 두 이벤트의 발송과 운영 반영을 수행한다. 이 문서는 승인한 작은 복원 범위와 L1 개발 검증을 고정한다.

```text
Platform 확정 이벤트 → 기존 서명 검증과 원장 저장
  신규 계정 → 최초 계정이면 기존 최초 카드, 이후에는 건별 한 줄
  새 버전 첫 유입 → 건별 한 줄
  각 이벤트 ID → 기존 알림 중복 키 → action-events → 앱운영이벤트
```

## 근거와 범위

2026-10-19 06:00 KST 확인: 최근 24시간 이벤트 49건(계정 42, 버전 4, 광고 보상 3)이 저장됐다. Discord의 마지막 메시지는 10-18 07:20 KST이며 이 채널의 대기와 영구 실패는 0건이다. #484에서 계정 요약과 버전 발송이 제거된 것이 원인이다.

신규 계정과 새 버전 첫 유입만 기존 한 줄 표시와 `operational:<eventId>` 키로 보낸다. 최초 계정은 기존 마일스톤 카드 한 건으로 충족하여 같은 이벤트의 두 메시지를 만들지 않는다. 등록되지 않은 앱은 원래 appId로 표시한다. 중복 이벤트도 enqueue 경로를 다시 실행하되 기존 outbox가 같은 메시지를 추가하지 않도록 한다. 보고 정책에는 `change` 분류로 명시하여 반복 성공 제외와 구분하고 보고 중지는 지킨다. 서명, 개인정보 허용 목록, 원장 스키마, 결제와 광고의 보고 기준은 바꾸지 않는다.

과거 48건을 일괄 전송하지 않는다. 배포 뒤 새 실제 이벤트로 확인하고, 새 이벤트가 없으면 수신 원장에 있는 최근 미발송 대상 한 건만 기존 서명 API로 재처리해 실제 전송과 동일 이벤트 재시도 시 무중복을 확인한다. 가짜 운영 이벤트나 직접 DB 쓰기는 사용하지 않는다.

## 인수조건과 검증

- AC-1: 등록 앱과 미등록 앱의 신규 계정, 새 버전 첫 유입이 한 줄로 action-events에 대기하고 보고 정책을 통과한다. 앱 이름, 실제 발생 시각, 제공된 버전과 런타임을 표시한다.
- AC-2: 최초 계정은 기존 최초 카드 한 건만 만든다. 같은 eventId 재전송과 원장 저장 뒤 enqueue 실패 재시도에서 알림이 한 건으로 수렴한다.
- AC-3: 결제, 광고와 장애의 기존 경로 및 보고 중지는 보존한다. 잘못된 서명과 금지 속성은 거부한다.

L1, dev/service-runtime. 실제 POST 라우트와 기존 원장·마일스톤·outbox 서비스를 실행하고 DB 경계만 격리 메모리 대역으로 바꾼다. 요구사항으로 실패하는 테스트를 먼저 확인하고 같은 흐름의 통과, 관련 알림·서명 회귀, typecheck, lint, build를 실행한다. 화면 개편이나 기기 의존 변경은 없다. 기존 키와 저장 계약을 그대로 사용한 일반 알림 생산자 복원이므로 중앙 backoffice 일반 변경 리뷰 예외를 적용한다.

## 적용과 복구

Ready PR, CI와 중앙 근거 검증 뒤 immutable 이미지를 만든다. schema와 worker가 바뀌지 않으므로 웹 Deployment만 이전 image와 resourceVersion을 검사하는 조건부 patch로 갱신한다. 기존 배포 identity 권한 검사와 data namespace의 provider audit 검증 상태를 먼저 확인한다. 전체 배포의 reconcile 실패 #517은 별도 미해결 상태로 유지하며 이번 웹 반영을 전체 롤아웃 성공으로 보고하지 않는다. 새 Pod digest와 readiness, 실제 이벤트 및 Discord 메시지를 각각 재조회한다.

실패하면 웹을 직전 immutable image로 되돌릴 수 있다. 기존 원장과 발송 메시지는 삭제하지 않는다. 자격증명과 공용 실행 설정은 변경하지 않는다. Version Impact: patch.
