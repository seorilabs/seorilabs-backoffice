# 배치 실행 결과 전용 채널과 지표 알림 문구 v1

- 설계 ID: BO-BATCH-MONITORING-20261024-v1
- 상태: 사람 검토 대기. 이 문서와 같은 폴더의 테스트 계획을 승인한 뒤 구현한다.
- 기준 소스: b1e3b612e28e532f68d9f9aee8361dc0abd7e7ca
- 요청 근거: 2026-10-24 사용자의 지표 알림 가독성 개선, 앱인토스 매 수집 성공과 실패 보고, 예약 작업 모니터링 전용 Discord 채널 생성 요청.
- 기존 설계: [서비스 배치 결과 알림](../2026-10-23-operations-batch-results/design.md). 이번 변경은 실행 결과의 목적지와 표시를 확장하며 수집 수치와 자료 완성도 원장은 보존한다.

## 바뀌는 동작

| 목적지 | 보낼 내용 | 발행 시점 |
| --- | --- | --- |
| 새 `배치모니터링`, 논리 목적지 `batch-monitoring` | 실행 성공과 실패, 처리 범위와 검증 결과 | 앱인토스와 KDP는 매 실행 종료 후 한 건 |
| 같은 채널 | 일반 예약 작업의 실행 결과 | 30분 이상 간격 작업은 종료마다, 더 잦은 작업은 완료한 직전 한 시간 요약 |
| 같은 채널 | 전체 운영 작업의 요약, 관측 공백과 예정 실행 미확인 | 기존 매일 09:00 KST |
| 기존 `장애알림`, 논리 목적지 `ops-alerts` | 실제 인증, 조회, 검증과 저장 실패 및 후속 복구 | 기존 장애 카드 경로로 즉시 |
| 기존 제품 지표와 판매 알림 채널 | 실제 지표 보고서, 판매 변동 등 기존 제품 보고 | 기존 주기 유지 |

채널 관찰: 서버는 `Seori Labs`(1538835016434589696), 카테고리는 `운영·분석`(1538852717458620437)이다. 기존 Backoffice 봇(1539211407629881346)은 메시지 전송 권한은 있지만 채널 관리 권한이 없다. `배치모니터링` 채널은 현재 없으며 채널 생성과 ID 확인이 운영 적용의 입력 조건이다. 다른 봇으로 우회하거나 관리 권한을 임의로 넓히지 않는다. 사용자에게 채널 링크를 요청한 상태다.

운영 감시 대상은 기존 platform, data, container-registry의 CronJob 34개와 로컬 KDP다. tasks와 개인피드는 기존처럼 제외한다. 실제 목록에는 매분 실행 작업 네 개가 있다. 성공마다 새 카드를 보내면 이 네 개만 하루 5,760건이 되므로 잦은 성공은 시간별로 묶고 실패는 즉시 보고한다. 감시자 자신도 시간별 상태와 관측 공백에 포함한다.

## 알림 예시와 상태

아래 수집 수치는 2026-10-24 15:30 실행에서 확인한 예시다. 실패 카드는 개발 검증용 합성 예시이며 운영 장애를 만들지 않는다.

```text
✅ 앱인토스 지표 수집 성공
10월 24일 15:30 실행
확인 기간 10월 10일~23일, 등록 항목 10개
저장 84건, 저장 대조 84건 일치
조회 오류 0건, 저장 오류 0건

자료 제공 상태: 일부 값 미제공
일부 지표만 확인 70개, 모든 값 미제공 56개
Android 광고 91개, iOS 광고 113개, 인앱결제 57개에서 날짜별 값 없음
항목별 숫자는 겹칠 수 있으며 값이 없는 항목을 0으로 바꾸지 않았습니다.
```

```text
❌ 앱인토스 지표 수집 실패
10월 24일 21:30 실행 — 개발 예시
실패 단계: 인증
오류: REAUTHENTICATION_REQUIRED
저장 여부: 확인 필요
조치: 등록된 운영 인증 상태 확인
```

```text
✅ 예약 작업 실행 결과
10월 24일 15:00~16:00 — 개발 예시
작업 대기열 점검: 성공 60회, 실패 0회, 진행 중 1회
앱 통합 관리 갱신: 성공 59회, 실패 1회
실패한 실행은 장애알림에서 별도로 확인합니다.
```

실행 결과와 자료 제공 상태를 분리한다. 공급자가 날짜별 값을 주지 않은 것만으로 실행 실패를 만들지 않는다. 제공된 값의 저장 실패, 저장 대조 불일치, 인증과 조회 오류, 대상 설정 오류나 요청 제한에 따른 미조회가 있으면 실행 실패다. 비정상 입력으로 저장이 제외된 경우도 성공으로 가리지 않으며 정상적인 대상 제외와 구분한다. 경고 문자열만 보고 실패를 추정하지 않고 원래 오류 종류와 저장 대조 결과를 사용한다.

기존 `complete`와 `partial` 자료 상태 및 실패 기록은 유지한다. `partial`을 `complete`로 덮어쓰지 않는다. 카드 제목과 색상은 실행 판정, 본문은 자료 제공 상태를 나타낸다. `결측`, `리스팅`, slug와 내부 ID의 긴 나열을 첫 화면에서 빼고 쉬운 한국어 이름과 실제 처리 건수를 우선한다. 미제공의 단위는 등록 항목과 날짜의 조합이며 오류 횟수와 다르다.

이번 변경은 Discord 카드 문구와 운영 경로 변경이다. 새 제품 화면과 웹 UI 개편은 없으므로 `redesign: false`다.

## 구조와 실패 처리

기존 SourceCollectionRun, NotificationEvent, NotificationDelivery, OperationalIncident와 outbox worker를 재사용한다. DB migration, 새 봇, 새 webhook, OAuth 교체와 지표 수치 보정은 없다.

1. `destinations.ts`에 `batch-monitoring`을 추가하고 기존 환경변수 규칙의 `DISCORD_CHANNEL_BATCH_MONITORING_ID`로 연결한다. 이 값은 공개 채널 ID다. 설정이 비었으면 운영 전 검증에서 중단하며 장애알림으로 성공 카드를 보내는 임시 fallback은 만들지 않는다.
2. 앱인토스 수집과 수동 push는 같은 실행 판정 기준과 카드 문구를 사용한다. 인증 검사 모드는 완료 알림을 만들지 않는다. 잠금으로 실제 수집을 시작하지 않은 요청은 실행 성공 횟수로 세지 않는다.
3. 앱인토스의 매 실행 결과는 새 채널에 한 건 보낸다. 실제 실패와 복구는 기존 장애 원장으로 장애알림에도 연결한다. 일반 감시자의 같은 Job 관측으로 카드가 중복되지 않도록 Kubernetes Job UID를 수집 결과에 결합한다. 프로세스가 결과 기록 전 종료하면 감시자가 최종 Job 실패를 근거로 보고한다. Pod 재시도만으로 Job 실패를 만들지 않는다.
4. 일반 작업은 Job UID, KDP는 기존 실행 UUID로 중복을 막는다. 같은 실행의 재관측은 새 카드를 만들지 않는다. 잦은 작업 요약은 KST 시간 구간과 작업 식별자로 한 번 생성하고, 종료된 창의 늦은 관측은 추가 기록과 정정 여부를 구분한다. 기존 원장 갱신을 사용자 알림 성공으로 취급하지 않는다.
5. 매 수집 카드는 배치 시작과 종료 시각, 지표 기준 기간, 저장과 대조 건수, 오류, 자료 미제공을 구분한다. 일부 저장 후 실패한 건수는 확인한 범위만 표시하고 미확인 값을 0으로 쓰지 않는다. 원본 응답과 비밀값은 카드에 넣지 않는다.
6. 서버나 알림 worker 자체가 멈추면 Discord 즉시 보고를 보장할 수 없다. 기존 감시 공백을 계속 기록하고 재연결 시 미관측 구간을 표시한다. 새 채널의 전송 실패는 기존 outbox 재시도와 실패 기록을 사용한다. 자료 재수집을 알림 재전송 수단으로 쓰지 않는다.
7. 과거 장애알림 메시지와 억제된 성공 알림은 지우거나 새 채널로 일괄 재발송하지 않는다. 운영 적용 이후 새 실행부터 경로를 바꾼다. 기존 장애 카드는 원래 목적지에서 복구까지 유지한다.

## 인수조건과 테스트

테스트 등급은 L1, 개발 환경 서비스 런타임이다. 같은 폴더의 [test-plan.json](test-plan.json)에 기준과 서비스 운영 적용 범위를 고정한다. 기기 사용은 없다.

| 조건 | 확인할 동작 | 방법 |
| --- | --- | --- |
| AC-1 | 전체 제공과 미제공만 남은 수집은 모두 성공 제목이며 자료 상태만 다름 | 판정과 카드 회귀 테스트 |
| AC-2 | 인증, 조회, 저장, 대조, 입력 거부, 실행 보류는 성공으로 가리지 않음 | 오류 단계별 격리 테스트와 CLI 종료 코드 확인 |
| AC-3 | 앱인토스와 KDP 실행마다 한 건, 동일 실행 재관측과 재전송은 중복 없음 | Job UID와 UUID, 순서 역전과 프로세스 조기 종료 테스트 |
| AC-4 | 실제 실패와 복구는 장애알림, 정상과 미제공 자료는 새 채널 | outbox 목적지와 장애 카드 수명주기 테스트 |
| AC-5 | 잦은 작업은 한 시간 요약, 다른 작업은 종료마다, 일일 집계와 개인피드 제외 유지 | 고정 KST 시계, 예정 실행과 중복 관측 테스트 |
| AC-6 | 84건, 일부 지표 70개와 전체 미제공 56개가 서로 다른 단위임을 카드에서 알 수 있음 | 실제 관측을 비민감 fixture로 정리하고 메시지 길이와 예시 확인 |
| AC-7 | 채널 ID 미설정과 전송 실패를 발송 성공으로 보고하지 않음 | Discord HTTP fixture, 영속 대기열과 재시도 검증 |
| AC-8 | 기존 수치, 명시적 0, 미확인 null, OAuth와 수집 일정 보존 | 지표 매핑 회귀, 배포 전후 읽기 전용 대조 |

요구 동작 때문에 실패하는 테스트를 먼저 만들고 구현 뒤 통과를 확인한다. 실제 채널 생성은 외부 권한에 의존하므로 API readback으로 이름, 서버, 카테고리, 접근과 전송 권한을 확인한다. `pnpm test`, `pnpm typecheck`, `pnpm lint`, `pnpm build`와 중앙 before-build 및 service before-deploy 검증을 수행한다. 필요하면 중앙 검증기가 요구한 추가 개발 환경 범위를 실행한다.

## 적용과 복구

설계와 테스트 계획 승인 후 실행 Issue, 구현, 로컬 MiniMax Code 리뷰, 한국어 Ready PR, CI와 병합, 명시한 서비스 운영 적용 순으로 진행한다. 운영 적용 범위는 Backoffice 웹, 알림 worker, 기존 배치 감시자와 앱인토스 collector의 같은 immutable 이미지, 실행 ID용 비민감 메타데이터, 새 공개 채널 ID와 필요한 경우 KDP 실행 결과 보고기다. OAuth, 수집 일정과 개인피드는 보존한다.

채널 입력이 해결되면 기존 비밀값을 출력하지 않고 현재 운영 설정의 보존과 복원 검증을 먼저 한다. 변경한 공개 채널 설정과 이미지의 실제 readback을 확인한다. 격리 테스트 후 실제 예약 실행을 관찰해 DB 대기열, SENT와 메시지 ID, Discord 실제 본문을 각각 대조한다. 앱인토스는 다음 정상 실행의 새 카드와 저장 대조를 확인하고, 장애 경로는 운영 장애를 만들지 않고 격리 환경에서 검증한다. 다음 자연 장애와 복구는 관측 전까지 미확인으로 남긴다.

문제가 생기면 이전 고정 이미지와 공개 채널 설정으로 되돌린다. 새 채널과 기존 원장은 삭제하지 않는다. 전체 원시 검수 자료는 NAS1dual 검증 보관 후 로컬에서 정리한다.

## 승인과 남은 입력

사용자 요청은 목표와 채널 생성을 명시한다. 위 시간별 묶음 기준, 실행과 자료 상태 분리, L1 테스트와 서비스 운영 반영까지의 구체적 설계 버전 승인은 아직 받지 않았다. 이 문서와 테스트 계획의 같은 커밋을 승인 대상으로 제시한다. 구현과 운영 반영은 승인 전 미실행이다.

추가 입력은 새 채널 링크다. 기존 봇에 관리 권한을 임의로 추가하지 않는다. 승인 후에는 정지 조건에 해당하지 않는 검수, PR, 병합과 정해진 운영 적용을 반복 승인 없이 진행한다.
