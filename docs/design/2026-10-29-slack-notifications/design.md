## 목적과 범위

Discord 모바일에서 채널 목록이 반복적으로 사라지는 문제 때문에 Slack으로 운영 창구를 옮긴다. 알림 13개 목적지, 기존 21개 명령, 이슈 초안과 등록, 장애 대응, 출시와 배포 승인, 대화와 메모, 본문과 이미지 첨부, 쓰레드, 정정, 리뷰 보존 정리를 포함한다. 기존 업무 서비스와 Backoffice의 권한 및 감사 경계를 유지한다. 개별 앱 마켓 출시와 심사 제출, 기기 접근, 유료 플랜 변경은 실행 범위에 없다.

GitHub는 코드와 이슈, Backoffice는 운영 설정과 대기열의 정본이다. Slack은 조회, 입력, 확인과 알림의 창구다. Discord의 과거 대화, 발송 이력, 기존 자격증명은 보존한다. 이전 서버와 채널은 삭제하지 않는다.

## 구현과 데이터 경계

`src/lib/operator`는 기존 업무 명령을 재사용한다. Slack 수신부는 원문 요청의 HMAC 서명, 5분 시간창, 워크스페이스와 앱, 채널, 사용자 결속을 확인하고 내부 요청으로 변환한다. Slack 사용자 ID의 업무 역할은 서버 설정으로 관리한다. 일반 이슈는 일회용 코드로 연결한 GitHub 계정의 앱 쓰기 권한까지 확인한다. 재전송 요청 ID를 원장에 한 번만 기록하고, 응답 URL과 봇 키는 저장하거나 로그에 남기지 않는다.

Slack 계정 연결과 일회용 코드, 대화, 요청 중복 방지 원장을 추가한다. 기존 명령과 장애 카드에는 제공 서비스를 구분하는 필드를 추가한다. 기존 Discord ID를 Slack ID로 해석하거나 다른 계정으로 자동 연결하지 않는다. 기존 DB column과 과거 이력은 유지하는 추가 migration을 사용한다.

알림 생산자는 `SLACK` 제공 서비스와 기존 논리 목적지를 기록한다. 전송 worker만 봇 키를 받는다. 정정은 기존 메시지를 편집하고, 삭제가 확인된 메시지만 새로 게시한다. 파일 할당, 업로드와 게시 결과는 영수증에 기록한다. 네트워크 중단으로 게시 여부를 알 수 없는 쓰기 요청은 자동으로 재게시하지 않는다. 쓰레드는 같은 채널의 원본 메시지 `thread_ts`를 사용한다. 본문의 임의 멘션은 이스케이프하고 명시적으로 설정한 운영자 멘션만 허용한다.

리뷰 원문과 요약 인용은 기존 30일 기준을 적용한다. 확정된 부분 성공 게시물과 첨부도 삭제 확인 대상이며, 결과 불명 요청은 정리 완료로 표시하지 않는다. 일반 운영 기록에는 별도 일괄 삭제를 적용하지 않는다. 과거 Discord 리뷰의 기존 보존 처리는 최소 삭제 경로로만 마친다.

## 인수조건과 검증

같은 폴더의 `test-plan.json`을 적용한다. 전체 운영 창구 전환으로 범위가 확대되어 L3 개발 환경 전체 회귀로 검증한다. 모든 회귀 실행은 독립 검증자 또는 확인한 CI가 수행한다. Backoffice 화면 개편과 네이티브 코드 변경은 없다.

| 조건 | 검증 |
| --- | --- |
| AC-1 목적지와 과거 이력 분리 | 신규 enqueue, 중복 요청, 제공 서비스별 claim, 과거 발송 보존 |
| AC-2 명령과 권한 보존 | 21개 명령, 입력 모달, 채널 범위, 계정 연결, 역할 회수와 고위험 확인 |
| AC-3 실제 응답과 재시도 | `ok:false`, 429, 5xx, timeout, 결과 불명, 삭제된 카드 대체 |
| AC-4 보고 내용과 파일 보존 | 지표, 리뷰, 장애, 배포와 예약 작업 본문, 링크, 이미지와 쓰레드 |
| AC-5 실행과 승인 중복 방지 | 요청 원장, 대기열 claim, 동일 요청자와 채널, 실행 직전 재권한 검사 |
| AC-6 리뷰 보존 정리 | 제공 서비스별 삭제, 부분 성공 영수증과 파일, 결과 불명 원문 보호 |
| AC-7 운영 연결 확인 | 앱 manifest, 권한, 모든 채널 참여와 공개 범위, 실제 게시와 같은 메시지 수정 |
| AC-8 실제 운영 전환 | 정확한 후보와 migration, 웹과 모든 소비자 이미지, 신규 자동 알림 수신, Slack 명령과 카드 실행 |
| AC-9 대기 작업 이관 | 이전 worker 정지, 미발송과 쓰레드 부모 이관, 열린 장애와 승인 재발행, 만료 확인과 감사, 재실행 안전성 |
| AC-10 Discord 신규 운영 중단 | Slack 검증 후 Discord 명령 해제, 이전 수신부 410, 신규 알림 경로 부재, 기존 서버와 이력 보존 |

요구사항 때문에 실패하는 전송 경계와 권한 회귀를 먼저 확인하고 수정한다. 외부 앱 등록과 자격증명 봉인은 합성 실패 테스트로 대체할 수 없으므로 manifest 대조, API readback, 백업 복원 검사로 검증한다. 기본 단위 테스트, DB fixture, migration 신규 설치와 구버전 전환, typecheck, lint, build와 worker 번들, 배포 스크립트 계약, 중앙 개발 근거 검증을 수행한다.

## 적용과 복구

실행 이슈는 [#548](https://github.com/seorilabs/seorilabs-backoffice/issues/548)이다. 코드와 DB, 새 수신부와 생산자 전환이 함께 동작해야 하므로 하나의 배포 후보로 검토한다. 기존 명령 로직 이동은 rename으로 확인한다. 제공 서비스가 섞인 중간 배포가 되지 않도록 전환은 다음 순서로 한다.

1. Slack 앱과 채널, 서버 권한과 서명을 공급자 응답으로 확인한다. 기존 자격증명은 보존하고 신규 Slack 키만 같은 Secret에 추가한다. 원본의 암호화 백업과 양쪽 복원 검사를 통과한다.
2. 후보의 전체 회귀, 로컬 코드 리뷰와 Ready PR 필수 검사, 중앙 배포 전 검증을 통과한다.
3. 운영 DB의 대기 작업과 각 배포 복제 수, 이미지, CronJob 일정과 실행 중 Job을 읽는다. 이전 notification과 operator worker를 정지해 신규 Slack 행을 이전 worker가 소비하지 못하게 한다. 실행 중인 이전 명령이 있으면 결과 확인 후 전환한다.
4. 호환 migration과 새 웹, worker, 관련 CronJob의 정확한 이미지를 적용한다. 이전 생산자가 더는 실행되지 않는 것을 확인한 뒤 전환 서비스를 실행한다. 미발송 알림과 필요한 쓰레드 부모만 Slack 배달을 만들고, 열린 장애와 대기 승인은 현재 상태로 재발행한다. 이전 미발송은 이관 사유로 보류 처리하며 발송 성공으로 바꾸지 않는다. 이전 확인 대기는 만료한다.
5. 새 worker를 시작하고 서명 검증, Slack 실제 명령, 확인 취소, 알림과 파일, 정정을 확인한다. 최초 자연 발생 알림의 DB 기록과 Slack 화면을 대조한다. 검증 뒤 Discord의 등록 명령을 해제하고 410 응답을 확인한다.

복구 시 worker부터 중지하고 적용 전 이미지와 설정을 사용한다. Slack 배달을 이전 Discord worker가 소비하지 않도록 대기열 제공 서비스와 신규 생산 중지를 먼저 확인한다. 새 migration과 원장, 기존 발송 이력은 되돌리거나 삭제하지 않는다. 실행 결과와 공급자 readback은 [setup.md](setup.md)와 실행 기록에 구분해 남긴다.
