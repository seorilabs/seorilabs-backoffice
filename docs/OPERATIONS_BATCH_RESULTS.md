# 서비스 배치 결과 알림

책 판매 변경, 앱인토스 수집의 저장 대조, 서비스 배치 실패와 복구는 `ops-alerts`로 보낸다. 그 밖의 실행 결과는 매일 09:00 KST에 직전 24시간으로 집계한다. 첫 연결에서는 직전 집계 구간의 부분 관측을 한 번 보고하며 도입 전 구간을 미확인으로 표시한다.

## 수집과 집계

`backoffice-batch-observer`가 매분 platform, data, container-registry의 CronJob과 Job을 읽는다. 기존 33개 서비스 배치와 감시자 자신을 포함한다. tasks의 개인피드 7개와 해당 영역의 북센, 교보 수집은 제외한다. SA에는 세 영역의 batch get, list 권한만 있다. Pod, 로그, Secret과 tasks에는 접근 권한이 없다.

Job UID를 실행 식별자로 사용한다. Pod 실패 횟수는 Job 최종 실패가 아니다. 같은 실행의 재전송은 중복 집계하지 않는다. 실행과 장애, 알림 대기열을 함께 저장하고 후속 실행 성공은 같은 장애 카드를 복구로 갱신한다. 늦은 과거 실패는 더 새로운 최종 상태를 되돌리지 않는다. 도입 전에 끝난 실패는 이력 집계에만 사용한다.

SourceCollectionRun의 `scheduled-batch`는 실행 원장이고 `operations-batch-observer`는 연결 상태와 일정 목록이다. 이 두 소스는 제품 지표 수집 상태에서 제외한다. NotificationEvent의 `operations-batch-daily:YYYY-MM-DD`로 보고 날짜를 중복 발행하지 않는다. 기록된 최종 완료 시각이 집계 창 안에 든 실행과 아직 진행 중인 실행을 센다. 진행 중 관측이 오래되면 최신 상태 미확인으로 표시한다.

일정에서 예정된 실행을 계산하지만 이력 보존 기간이 지난 실행은 복원할 수 없다. 150초를 넘는 감시 간격, 첫 도입 전 구간과 예정 미관측은 성공으로 추정하지 않는다. 일부 배치의 성공 이력은 2개만 남기므로 감시 중단 뒤 사라진 실패를 모두 알아낼 수 없다. 감시자나 서버 자체가 멈추면 즉시 서버 알림은 보장할 수 없으며 다시 연결됐을 때 공백을 기록한다.

프로세스 성공은 자료 완성도 검증과 별개다. 앱인토스는 이번에 제공된 날짜별 값, OS별 광고 원값과 새 collectedAt을 DB에서 다시 읽어 대조한다. 공급자 미집계는 0으로 만들지 않는다. 파드 수집과 기존 수동 push 모두 결과를 알린다. 과거에 억제한 수집 알림을 일괄 재발송하지 않는다.

KDP는 월별 판매 행의 내용 변경만 알린다. 파일 해시와 수집 시각만 달라진 재수집, 늦게 도착한 과거 관측은 알리지 않는다. 정정으로 사라진 행과 이전 값으로 돌아간 정정도 새 실행으로 알린다. 예상 로열티는 통화별로 표시한다. 로컬 수집기는 월별 저장 결과를 다시 읽고 전체 실행의 시작, 완료와 검증 월 수를 보고한다. 서버에 연결하지 못하면 로컬 실패만 남는다.

## 운영 반영과 복구

승인된 운영자는 먼저 `k8s/operations-batch-observer-rbac.yaml`을 적용한다. CI 배포 계정의 권한은 늘리지 않는다. 중앙 개발 검증, PR 검사와 병합 후 명시 배포를 실행한다. 배포는 감시자 매니페스트를 적용하고 기존 앱인토스 CronJob은 이미지 필드만 갱신한다. OAuth 참조와 6시간 간격은 보존한다.

KDP는 병합된 커밋에서 `install_launchd.py --replace-source <기존 40자리 SHA>`로 교체한다. 현재 설치 해시, 소유자, 명령, 일정과 실행 여부를 먼저 검사하며 변경된 설치는 보존하고 중단한다. bootstrap 실패 시 이전 plist와 launchd 등록을 복구한다. 매일 09:00 KST 일정과 인증 프로필은 유지한다.

장애 시 감시자 CronJob을 suspend한 뒤 이전 고정 이미지로 복원할 수 있다. 기존 SourceCollectionRun, 알림과 장애 원장은 삭제하지 않는다. 앱인토스는 이전 이미지로 되돌리며 OAuth 참조를 수정하지 않는다. KDP는 검증된 이전 설치의 plist로 복구한다.

검증에서는 DB 대기열 등록, Discord SENT 상태와 메시지 ID, 실제 채널 조회를 구분한다. 가짜 판매나 장애를 운영에 만들지 않는다. 실제 판매 변경과 다음 자연 예약 실행은 관측한 뒤 별도로 확인한다.
